## 1. System overview

```

                         │  Desktop app (Tauri 2)                                          │

                         │   └─ Rust backend                                               │
                         │        ├─ Session host (authoritative state, command handling)  │
                         │        ├─ LAN server: HTTP (companion static files) + WebSocket │
                         │        ├─ Storage: library folder, file watching, previews     │
                         │        ├─ Light drivers (HA, Hue, WLED, Govee, Nanoleaf)        │
                         │        └─ Camera pipeline (OpenCV/ArUco)            [stage 7]   │
                         └──────────────┬─────────────────────────────┬────────────────────┘
                                        │ WebSocket (LAN)             │ local folder
               ┌────────────────────────┴───────┐            ┌────────┴──────────┐
               │ DM remote (browser)  [stage 3]  │            │ Cloud client      │
               │ Player companion (browser)[st.3]│            │ (Dropbox, iCloud…)│
               └─────────────────────────────────┘            └────────┬──────────┘
                                                                       │ sync
                                              Obsidian / Markdown tool (offline planning)
```

Two independent channels:

- **Live channel (LAN WebSocket):** only during a session. Desktop is the single source of truth.
- **Data channel (sync folder):** files on disk, synced by a third-party cloud client. Used for planning on the go.

## 4. Module boundaries (enforced by dependency-cruiser)

| Package    | May depend on                                                         | Must NOT depend on                                     |
| ---------- | --------------------------------------------------------------------- | ------------------------------------------------------ |
| `core`     | `schema`, `polyclip-ts` (pure polygon boolean ops for fog)            | React, PixiJS, Tauri, Expo, Node/Browser APIs, any I/O |
| `schema`   | zod                                                                   | everything else                                        |
| `protocol` | `core`, `schema`, `zod` (message validation)                          | UI, renderer, I/O                                      |
| `storage`  | `core`, `schema`                                                      | UI, renderer; real FS (uses an injected adapter)       |
| `renderer` | `core`, `schema`, PixiJS                                              | React, Tauri, storage                                  |
| `ui`       | `core`, `schema`, `i18n`, React, `renderer` (public entry point only) | Tauri, Expo, renderer internals                        |
| `apps/*`   | any package                                                           | other apps                                             |

Rules:

- `core` is **pure**: deterministic functions, no clocks, no randomness without an injected source, no I/O.
- Platform-specific code lives only in `apps/*` behind adapters (FS, network, clock, RNG, lights, camera).

## 5. Domain model & state

### 5.1 Command → state → events

All state changes go through **commands** handled by a pure reducer in `core`:

```ts
apply(state: SessionState, command: Command, ctx: Ctx): { state: SessionState; events: DomainEvent[] }
```

- `Ctx` provides injected time and RNG (deterministic tests).
- **Permissions** are checked in `core` (`canApply(actor, command, state)`): DM, DM remote (web app), player companion (per-player rights).
- **Undo:** each open document (a scene today; maps, assets and creatures as they become documents) keeps its own history of earlier states – snapshots, cheap because states are immutable and share unchanged parts (`History<T>` in `core`; DM decision 2026-11-20, T-174). A history lives until its document closes or the app quits and is never stored. Undo and redo (keys and title bar) act on the document of the workspace that shows; documents of other workspaces stay mounted but do not react, and leaving the Game-Orchestrator drops a fog tool back to panning.
- **Session log** is derived from `DomainEvent`s. Events that leave the host (the log shown to players, any broadcast) first go through `projectEvents(events, stateAfter, viewer)` in `core` (T-117), once per `apply` result – never for older events against a later state, which would leak what was hidden at the time; a log keeps the projected events. An event passes only when its subject shows in `projectForViewer(stateAfter, viewer)` and with no more detail (HP exact or coarse as projected, moves without their origin); visibility changes and removed combatants never pass. The output is checked against the strict `viewerEventSchema`.
- **Visibility filtering** (`projectForViewer(state, viewer)`) is a pure function in `core`. The player window and every companion only ever receive the projected state – hidden data never leaves the desktop. It builds its output from an explicit allow-list with strict viewer schemas – never by parsing with the (loose, unknown-field-preserving) file schemas from `packages/schema` or by spreading state objects. Asset references in a projection are capabilities: a companion must never receive a reference that lets it fetch an un-fogged map or a level that has not been revealed (T-118a: only the table view gets them; companions get fog-composited images, T-118b).

### 5.2 Key entities (initial)

`Campaign`, `Scene`, `MapData` / `AssetData` (sidecar: metadata, scale, levels, walls, doors, lights, rooms; for assets mask, blocker type, variants – ADR-0012), `SceneOverrides` (per element id), `PlacedAsset`, `Token`, `FogState` (revealed regions per level, memory fog), `InitiativeState`, `Combatant` (HP, temp HP, conditions), `VisibilityRule`, `Player`, `Handout`, `SoundPreset`, `LightPreset`, `WikiEntry`.

Coordinates: grid cells (integer `col,row`) for game logic; map pixels for rendering. Conversion lives in `core`.

The entities are zod schemas in `packages/schema`. Only the files carry `schemaVersion` – `campaign.json`, one file per scene and one per session (version 2 since T-119: lowercase ids) and one sidecar per library file (ADR-0012); the other entities are embedded in them.

A scene references its map (ADR-0012) and keeps overrides by element id; `core` resolves the effective map with a pure `resolveMap` (the sidecar's map data plus the scene's overrides) that renderer, vision and `projectForViewer` all use. `SessionState` carries the resolved map next to campaign and scene, so commands and projection never read map data from the scene file (T-134). A sidecar (`sidecarSchema`, version 1) holds a map's grid, levels (archived levels stay resolvable) and rooms; every element id is unique within the map. A level that a scene still refers to (fog, tokens, TV state) is archived instead of deleted (`removeLevel`). Overrides whose target id no longer exists stay stored, are inactive and are reported as orphaned. Grid and scale are never overridden per scene. A global edit reaches a scene that is live on the TV only after the DM confirms it. Unknown fields are kept on round-trip, documents from a newer app version are refused instead of downgraded, and older ones are migrated step by step (`migrateDocument`).

## 6. Storage

### 6.1 Principle

All data lives in a **user-chosen folder**. If it sits inside a cloud-synced folder, the cloud client does the syncing. The app never calls cloud APIs.

### 6.2 Folder layout

```
<library root>/
├── library/                  # global asset library (all campaigns)
│   ├── maps/  tokens/  assets/  sounds/  effects/
│   ├── creatures/            # one JSON file per creature, in folders the DM makes (ADR-0018)
│   │   └── castle.webp + castle.webp.dm.json   # sidecar per file (ADR-0012)
│   └── .previews/            # generated by desktop for the web app and handouts
├── campaigns/<campaign-slug>/
│   ├── campaign.json
│   ├── wiki/                 # Obsidian-compatible Markdown + YAML front matter
│   ├── sessions/             # one JSON file per session: name, date, ordered scene ids (T-160)
│   ├── notes/                # campaign.md, sessions/<id>.md, scenes/<id>.md – fixed notes (T-161)
│   ├── scenes/               # one JSON file per scene
│   ├── characters/           # player characters, in the creature format (ADR-0018)
│   ├── encounters/
│   ├── snapshots/            # ZIP per session
│   └── .trash/               # 30-day trash
└── (no device settings here)
```

Device-specific settings (light devices, cameras, TV calibration, window placement, recently edited campaigns) live in the OS app-data directory, **not** in the sync folder.

**Rescue copies (T-114b, DM decision 2026-11-20).** When saving a scene fails (e.g. the cloud folder is unreachable), its latest state is kept on this device in the webview's storage (`dm.rescueCopies`: `{ version: 1, copies: [{ root, slug, savedAt, scene }] }`, one copy per scene) – never in the sync folder. A later successful save of the same session drops it; a copy from an earlier session is newer than the scene opened from disk, so only the DM drops it – by restoring it (written to the library with `saveScene`, which validates it; an open tab shows it, with a fresh history) or discarding it – or deleting the scene does. The offer shows in the map's notices when the campaign opens (also after a crash). Copies are read like scene files: migrated from an older scene version, then validated; entries this app cannot read are skipped but kept as they are, and copies for other library folders stay until that folder is used again.

Sub-scenes (T-152): a scene file may name its parent scene in an optional `parentSceneId` (DM decision, 2026-11-19): additive, so no version bump and no migration – older readers keep the field, older scenes simply have none. A sub-scene is its own scene (own map, fog and tokens), nesting to any depth. A parent that is missing (deleted, not synced yet) makes the scene a top-level scene, and so does a loop written by hand (also a scene naming itself) for the scenes in the loop, so none disappears. Deleting a scene with sub-scenes asks: keep them (preselected; they move up to the deleted scene's parent) or move them into the trash too.

Levels on the TV (T-118a): a scene file may carry an optional `table: { levelId, shownLevelIds }` (DM decision, 2026-11-19; additive like `parentSceneId`): the level the TV shows and every level shown there so far. A level once shown stays released for players; ids of levels the map no longer has are ignored, and without `table` the TV shows the map's first level. The DM switches it with the `level.show` command (undoable; showing the level already on the TV changes nothing and adds no undo step, and the level shown before stays released). In the DM window the level the DM works on and the TV's level are separate (T-118c, DM decision): a "Ebene" group in the Szene tab – only for maps with more than one level – picks the working level (fog tools, its own image or video by file type) and shows it on the TV; the browser marks the TV's level and the released ones. `projectForViewer` lists only released levels with their fog and tokens (not even an own token shows on an unreleased level, its level id would give the level away – nor, therefore, its combatant in the initiative) and gives asset references only to the host-rendered table view; companions get fog-composited images instead (T-118b).

Fog biomes (T-168, DM decision 2026-11-22; additive like `parentSceneId`, no version bump): a sidecar's map data and a scene may carry `fogEffect: { biome, strength }` (strength 0–1). The scene's own (chosen live with the undoable `scene.setFogEffect`) wins over the map's (`effectiveFogEffect`); the biome is an open name in files, so a newer app's survives, but `projectForViewer` passes only the eight known biomes, field by field, as a strict `fogEffect` of the viewer scene. The map's default is set in the Map Forge (T-176).

Grid mode and combat (T-233, DM decision 2026-11-21; additive like `parentSceneId`, no version bump): a token's `position` is in cells from the grid's origin (its top left corner) and may be fractional when placed freely – cells, not map pixels, so it does not depend on the image's resolution. Grid cells for footprints and occupancy stay whole. A scene may carry `gridMode` (`grid`, `gridInCombat`, `free`); without one the campaign's `gridMode` applies, without that `gridInCombat`. `combat: true` is game state and survives a restart. The `combat.start` command (with the map's whole cells as bounds) snaps every token to the nearest free cell, level by level, in one undo step – one token per cell, up to four Tiny ones per cell, large footprints whole, nearest token first – and is rejected when one finds no room; `combat.end` leaves tokens where they are. Tokens the table does not see never push one it sees aside (DM decision 2026-11-21, T-233b): tokens the TV shows (released level, not hidden, centred in revealed fog – `seenByTable`) snap among themselves first, the others then fit around them – nothing is given away, and a seen token may end up on an unseen one's cell. Snapping may move an unseen token into revealed fog, where the TV then shows it. Moves onto the grid (`token.moveMany` with the map's cells as `bounds`, T-233c) never end on an occupied cell, in or out of combat: a token whose cell is taken goes to the nearest free one, with the same rule for what the table sees (DM decision 2026-11-21: not back to where it was). Tiny tokens sharing a cell arrange by count (middle; side by side; triangle; quarters), counting only the tokens given – on the TV the projected ones, so nothing hidden shows; Small tokens are drawn at 75 % of their cell. Free movement (T-233d): whether a move is free follows the scene's grid mode (`scene.setGridMode`, undoable; else the campaign's, else `gridInCombat`) and combat, or Alt held. A free move (`token.moveMany` with `free`) keeps its exact position (to a thousandth of a cell) and never overlaps another token's disc (drawn size: Tiny ½, Small ¾, otherwise the footprint): a token dropped onto another is pushed just far enough away, the nearest spot first, of equally near ones the one nearest to where it came from – with the same rule for what the table sees. Arrow keys move one cell in either mode. The campaign's default (T-233e) is set in the settings dialog's "Kampagne" tab and written into `campaign.json`; the campaign panel reads it back at once (and on changes on disk) and hands it to its open scenes. A token placed freely takes every grid cell its disc reaches into by more than a tenth of a cell (T-242, DM decision 2026-11-21), so a token on the grid never overlaps it. A free Tiny token takes those cells whole (T-243), so Tiny tokens arranged in a cell's quarters never lie over it. Moved tokens glide to their new place on the TV and in the DM window (not while dragged); the combat switch sits in the Szene ribbon while playing. The TV's projection carries `combat: true` while it runs. Older app versions reject a scene with a fractional position (they expect whole cells).

Initiative (T-111a): combatants may carry `initiativeBonus`, `playerId`, `delayed` and `ready` (additive). Turn order is by initiative, then bonus, then players before creatures; a combatant added later goes behind the last one not ranking below it, so an order changed by hand stays. Rolls are made by the caller (`rollInitiative`, injected random) and carried in the command, so undo and redo stay deterministic. `initiative.start` starts combat (the snap) and round 1, `initiative.end` clears the initiative and ends combat, each as one step; delayed combatants are skipped (also when the active one is removed) until `initiative.actNow` puts them before the active one; if all have delayed, the next one acts and is no longer delayed. On the TV (T-111c) the active combatant's token shines (a bright ring, also in the DM window) and an initiative bar along the players' top edge – turned with the TV's view – lists the projected combatants from the first turn on, the active one marked; it shows only what `projectForViewer` gives the table (hidden combatants left out, withheld names as "Unbekannt"). The panel (T-111d) also takes the players' rolls in one keyboard form, applied as one step (`initiative.enterRolls`: a character joins with the player's token – on the shown level first – or, found by its player or the player's token, gets its new value) and free entries without a token (hidden on the TV until released), and reorders by drag as well as by its up/down buttons. HP and conditions (T-112a): `hp.set` starts tracking a combatant's HP or corrects them (temporary HP stay); `condition.add` replaces a condition of the same type, `condition.remove` takes one off. When a new round starts (not the first), every condition with a duration counts down by one and goes at 0 – the round, not a turn, counts, so a restarted turn ("act now") never counts twice (DM decision 2026-11-21). HP show only in the Initiative panel (DM decision), never on tokens or the TV. In the panel (T-112b) each combatant's row shows its HP (with temporary HP) and conditions on a line of its own: a popover takes damage, healing, temporary HP and corrections (or starts tracking), another adds one of the 5e conditions with or without rounds; a chip's ✕ removes it. Exhaustion has a level (T-244, DM decision 2026-11-22): an optional `level` 1–6 on the condition (additive), raised and lowered in the panel, gone below 1; it stays in the panel, the TV's projection never carries it.

Notes (T-161): every campaign, session and scene has a fixed Markdown note in `notes/`, created on demand with the title as a heading and never overwritten. Any other `.md` inside the campaign folder can be linked through an optional `notes` list (paths relative to the campaign folder, validated: inside the folder, `.md`, no tool folders) in `campaign.json`, a session or a scene file. The app reads notes as they are, so their front matter and links survive (ADR-0006).

### 6.3 File rules

- **One file per entity.** Never a single database file in the sync folder.
- Every JSON file has `schemaVersion`. Reading runs migrations in `schema`; writing always uses the latest version.
- **Ids are lowercase** (`a–z`, digits, `-`, `_`; T-119) because they name files, and `Scene-1.json` and `scene-1.json` are one file on macOS and Windows. Version 1 files may hold capitals: the migration to version 2 lowercases every id and every reference the same way and refuses a document in which two ids differ only in case. A version 1 file name with capitals is listed under its lowercase id; on a case-sensitive file system (Linux) it is found ignoring case and moved to the lowercase name on load, the old file going to the trash. Leftovers (T-234): a document refused because two ids differ only in case names both ids to the DM (the browser and library list say which, so the DM renames one in the file); on a case-sensitive file system a version 1 name next to the current lowercase file is listed like a conflict copy (`provider: "capitals"`) and shown under its scene or session; own notes (`notes/scenes|sessions/<id>.md`) are listed under the lowercase id, found ignoring case and moved to the lowercase name like documents (also before "Notiz öffnen" would start a new one). Characters and creatures get the same `capitals` conflicts from storage; no list shows conflicts for them yet.
- **Sidecars** (`<file>.dm.json`, ADR-0012) are read and written like documents (`loadSidecar`, `saveSidecar`): atomic, validated, placeholders and broken files reported, never thrown. A missing sidecar means defaults. Unlike id-named documents they are looked up by their exact name only. The watcher reports them as `sidecarFile`, and their conflict copies are found by `listSidecarConflicts`. Since scene version 3 a scene stores only `{ kind, asset, overrides }` for its map; a version 2 scene keeps its own grid and levels as `legacyMap` until `settleLegacyMap` (run when the scene opens) has moved them into the map's sidecar by `adoptLegacyMap`: the first scene seeds it; a later scene whose grid or levels differ in any way (ids, names, images, order) keeps its copy for the DM to adopt or discard, so nothing is lost silently. A new scene's map and a changed map get their sidecar from `ensureMapData`, which never overwrites existing map data or a sidecar that is not available. Besides `map`, a sidecar may hold `info` (T-125, DM decision 2026-11-22): a catalog item's `name`, `origin` and `license`, all optional, the same block for maps, tokens and assets; `updateItemInfo` writes it (creating the sidecar if needed, trimming, leaving blank fields out, never overwriting an unavailable sidecar) and `listLibraryMaps` reads it, so the catalog shows and searches the name. The DM edits it by selecting a tile in the data panel's catalog: the Eigenschaften panel then shows the item instead of the browser's selection, until something is selected in the browser again (`CatalogSelectionContext`). The DM window resolves the open scene's map from the sidecar (`useMapData`) and reloads it when the sidecar changes on disk – the open scene is on the TV, so a change that differs from what is shown waits until the DM accepts it (T-134b); while the data is not available, the map is not shown.
- Asset references are **relative paths from the library root** plus a content hash, so moved/renamed files can be re-linked.
- Writes are atomic: write to `*.tmp`, then rename.
- **Conflict detection:** recognise conflict copies of common providers (e.g. `name (conflicted copy …)`, `name (1)`, `name-DESKTOP-XXXX`) and offer a diff/merge UI. Never silently delete either version.
- **Placeholders:** files not yet downloaded (on-demand sync) must yield a "not available yet" state, never a crash.
- **Desktop file access:** the webview only passes library-relative `/` paths to the Rust backend, which confines them to the chosen root (no `..`, drive colons, backslashes, Windows device names or symlinks below the root; temporary files are created exclusively, never through a symlink). Known gap: the symlink check runs just before each operation, so a sync peer swapping a folder for a symlink in between is not caught – accepted, because the webview cannot create symlinks. Imported assets are copied once into a staging file (hashed on the way) and placed with a hard link, which never replaces an existing file; on volumes without hard links a rename after an existence check is used, with the same kind of small race. The root is only set through the native folder picker (or the saved device setting), never by the webview. Only the DM window's capability grants the `library_*` commands; changes on disk are reported to the DM window by a `notify` watcher.
- Changing the folder layout or a file format is a **breaking change** → requires DM approval and a migration (see CLAUDE.md).

### 6.4 Notes

Markdown with YAML front matter (`type`, `status`, `tags`, …) and `[[wiki links]]`; must remain readable and editable in Obsidian.

### 6.5 Previews

Desktop generates downscaled images (and a still frame for video maps) into `library/.previews/` for the catalog, the web app and handouts; originals stay on the notebook.

- **Map catalog (T-124):** `listLibraryMaps` (`storage`) lists every image and video under `library/maps/` (recursively, for all campaigns; hidden files and sidecars are no maps, a sidecar's conflict copies are listed with their map). A preview is named after the content hash of the file it shows: `library/.previews/<hex>.jpg` (`previewFile`), so a renamed or moved map keeps its preview and a changed one gets a new one. JPEG, not WebP: WebKit (macOS, Linux) cannot encode WebP, and maps are opaque. The DM window draws a missing preview itself (canvas, at most 384 px on the longer side; a video's first frame, loaded CORS-clean and not played) and hands it to `library_write_preview`, a DM-window-only command that accepts only a well-formed `sha256:` hash, at most 1 MiB, and JPEG bytes, and writes only into `library/.previews/` (DM decision: no image library in the backend). The content hash comes from `library_hash` (DM window only, files under `library/` only, never sidecars), which reads the whole file: a tile starts hashing and drawing only once it comes on screen, at most two at a time, and queued work is dropped when no tile wants it any more. Hashes are kept for the session only (a lasting path → hash record is a follow-up). Previews are read back like note images (`library_read_image`); a preview that cannot be stored is still shown. The DM picks a scene's map in a dialog with the catalog's grid of previews, a search and the import of a new file; the data panel shows the same grid. Deleting a scene never touches the catalog.

### 6.7 Obsidian vault and scene drafts

The DM plans on the go in Obsidian or any Markdown tool (ADR-0013). Storage ignores tool folders such as `.obsidian/`; the desktop watches notes and picks up external changes. Notes with scene front matter (`type: scene`, map, sound, light, tokens) are validated with zod and offered as scene drafts; invalid ones show an actionable hint, never a crash.

### 6.6 Backups

- Snapshot ZIP per session end (campaign data only; assets are referenced, not included)
- Trash with 30-day retention: deleting moves a file to `campaigns/<slug>/.trash/<UTC timestamp>[-n]/<path inside the campaign>`, so it can be restored to where it was (never removed, never overwritten); purging after 30 days is still to be built
- Export: self-contained archive including used assets
- Sharing a single map or asset: `.dmmap` bundle (ZIP of original, sidecar and variant files; ADR-0012)

## 7. LAN networking

- Desktop backend runs HTTP + WebSocket bound to the local network interface only.
- HTTP serves the built `apps/companion` bundle.
- **Pairing:** QR code contains `http://<lan-ip>:<port>/?t=<one-time token>`. The token is exchanged for a session credential; tokens expire and can be revoked by the DM.
- Roles: `dm` (desktop), `dm-remote` (DM mode of the web app, own pairing), `player:<id>` (companion).
- Messages are defined and validated in `protocol` (zod). Every message has a `v` (protocol version). Clients send **commands**; the host validates permissions, applies them, and broadcasts **projected state patches** per viewer.
- Clients are disposable: on reconnect they receive a full projected snapshot.

## 8. Rendering (PixiJS)

Layer order (bottom → top): map (image/video) → grid → assets → light/vision → tokens → effects → fog → DM overlays (DM window only) → UI pings.

- The **same renderer** draws the DM window and the player window, with different viewer projections and overlays.
- The player window is a separate Tauri window placed fullscreen on the chosen display. Its only permission is listening for events – which Tauri cannot limit to certain events, so the player window can hear every global event of the app. Hence the rule: **no global event may carry library or campaign data**; data meant for the DM window only (e.g. file changes) goes through IPC channels, and drag & drop is disabled. With that permission: the DM window sends it a versioned `PlayerViewMessage` (`protocol`) with the scene as `projectForViewer` leaves it for the table, and the player window validates every message with the strict schema. When the player window (re)loads, the backend tells the DM window, which sends the current state again. The message may carry the TV's calibration (T-106a/d): `scale: { inchPx, cellInches }` from the check square the DM measured on that display and the cell size set in the settings (device storage `dm.displayCalibration`, `dm.tvCellSize`) – the player window then shows one grid cell at that size instead of fitting the map – and `checkSquarePx`, a square of that many physical pixels shown while the DM calibrates. `viewCenter` (map pixels) is where the calibrated TV centres – the DM drags a frame of the TV's view on the map of the scene on the TV (T-106c). `showGrid: true` draws the scene map's grid lines on the TV (T-106b, off by default); the renderer draws them between the map and the fog, so fogged areas stay black, lines included. Tokens (T-107a) are drawn on top of the grid and under the fog as well – on the TV only the projected tokens of its level; until the creature library (T-180) each is a disc in a colour from its id with its initials and a ring. The player view fails closed: opaque fog covers everything not revealed, it is set before the map, and without a valid scene the screen stays black.
- Grid calibration: the target display's pixels per inch, measured by the DM on a check square of a known size (per display, `dm.displayCalibration` version 2; T-106d) × the cell size from the settings (`dm.tvCellSize`, inches or cm, 1 inch by default) → view pixels per cell.
- Library images reach the webviews through the read-only `dmlib` URI scheme (Rust, `protocol.rs`): it serves only files under `library/` with the usual path confinement, only to the DM and player windows, and never `campaigns/` (scenes, notes, hidden data). It replaces any file permission for displaying maps. Image maps are uploaded as WebGL textures, so responses are CORS-clean. Video maps (MP4/WebM) are served in byte ranges of at most 4 MiB (HTTP Range), never read whole into memory; the CSP allows `dmlib` for images and media only.
- Note images (T-163) do not use `dmlib`: the DM window reads them with `library_read_image`, a command only its capability grants (PNG/JPEG/WebP/GIF by content, at most 20 MB, path confined like every library command) and shows them as blob URLs. The CSP's `img-src` also allows `https:`, for external images in notes that load only after the DM clicks "Bild laden" (no referrer). Tauri has one CSP for both windows, so the player window could load https images too; it renders no notes and no untrusted markup.
- Fog is an opaque layer with the revealed polygons as an inverse stencil mask (each polygon filled on its own), so nested and touching areas render correctly; the player view draws it opaque, the DM view see-through. **Soft edges (T-136a)**, on by default and switched per device in the settings: once per fog change (never per frame), the revealed polygons are rasterized into a mask of at most 1024 texels per side, shrunk by half the edge width plus one texel and box-blurred by half the edge width (`soft-mask.ts`, pure), then stretched over the map with linear filtering. The edge is 0.25 grid cells wide, from the hard edge inwards, so a revealed one-cell corridor stays open in its middle. An unchanged fog request (same polygons, options and map size) keeps the built fog. A discarded fog layer is freed completely (`disposeFog`, T-165): its graphics with their contexts, and the textures its sprites and meshes own – never the shared `Texture.WHITE`. The player view keeps the exact hard fog underneath, so the soft layer only darkens and the result never shows more than the hard polygons (fail-closed, pixel-tested); the see-through DM view uses the soft layer alone. Fog set before the map stays hard until the map's size is known. The player window reads the setting from the shared webview storage and follows the DM window's changes through the `storage` event; should a webview not deliver it across windows, the player window still picks the setting up on its next start. The see-through DM view tints only the map area (nothing else is drawn there). **Fades (T-136b):** a fog change within the same map fades over the duration set per device (0–3 s, default 0.65 s, ease-out; 0 switches at once), hiding too (DM decision). During a fade the exact hard fog covers everything fogged in all of the fade's states (its open area is the union of their revealed areas), and over the map a small shader blends the masks before and after texel by texel – linearly, so a pixel fogged before and after never shows the map (pixel-tested); two see-through layers on top of each other would let it shimmer through. **The change spreads (T-167, replacing the uniform cross-fade – DM decision):** once per change, `fog-spread.ts` (pure) gives each changed texel the moment it turns over, on a grid of at most 256 texels per side (about 5 ms; the order only sets the timing, the linear mix keeps the fog safe): connected texels changing the same way spread on their own over the whole duration – a reveal from the revealed area it touches, else from its middle outward; a hide from the fog it touches, else from its middle outward (T-249, DM request: a large area hidden on its own closes from its middle) – with chamfer distances inside the change, so a spread follows corridors around corners; the map's border counts as an edge (a change of the whole map clears and hides from its middle). "Alles verdecken" on a fully revealed map starts where the device's setting says (`coverFrom`, T-249, settings dialog "Alles verdecken beginnt"): at the map's middle (default) or at a point that looks random – the changed texel at a share hashed from the revealed polygons before and the map, so the DM window and the TV practically always pick the same point without a protocol change (a cover-all during a running spread or hand-edited polygon fields can shift it slightly – cosmetic); it applies only when the map's whole mask ends fogged (revealed slivers beyond the map's border do not count) and only within a scene and is not part of the fog's rebuild key, and a change without length (one texel, a one-texel line) turns over at once. Unchanged texels next to a change carry its order, so the linearly filtered order texture does not pull the change's edge ahead of its front. The shader mixes each texel while a soft front (a fifth of the spread) passes it; `spreadMix` does the same on the CPU with nearest sampling of the order (used only to restart from what is on screen, where small differences at edges are harmless). A change during a fade starts from what is on screen so far. The exact fog that takes over at the end is built when the fade starts, so its last frame costs nothing extra. Only a fade (and drifting living fog, below) draws every frame; the first fog, a new map (also one of the same size) and a new scene never fade, and the fade duration is not part of what counts as an unchanged fog. Without soft edges a fade blends texel-sized hard masks, so edges look slightly soft while it runs; in the DM view it tints only the map area during the fade. **At a speed (T-246, ADR-0019):** the DM window and the TV pass the device's speed (grid cells per second, 21 steps from 0.5 to 40 in roughly even ratios on a slider in the Nebel ribbon's Ausbreitung group, 5 by default, its last step "Sofort") with the map's cell size and a seed from the map's path. Then every change travels at that speed instead of over a fixed duration: `coarseSpreadOrder` times all changes against the longest one (a small change finishes first) and walks a cost field of value noise in grid cells (`raggedWeights`, costs 1–12, seeded by the map's path – by its size if no seed is given – so the same map spreads the same way in the DM window and on the TV), so the front advances in tongues; the travel time is the length, in plain steps, of the path to the texel the front reaches last, so the set speed holds along it. Weighted, the order costs about 20–50 ms for a change over the whole 256² grid (Node; the plain one about 18 ms), once per change; "Sofort" builds no ragged order. The fade duration becomes the time each spot takes to turn over ("Übergang", 0–3 s, DM decision 2026-11-22: 0 stays, and with "Sofort" it switches at once as before). `spreadAtSpeed` splits the duration into the front's travel and the last spot's turn; the shaders and `spreadMix` take these shares as uniforms instead of the fixed fifth, and a spread at a speed runs evenly (not eased). A changed speed applies to the next change and redraws nothing (like the fade, it is not part of what counts as an unchanged fog). A new scene or level never spreads at any speed: the TV passes a speed only for changes within the scene. Fog edits run through `core` (`execute` with undo history) in a scene session in the DM window, which saves each change to the scene file and sends the TV the new projection synchronously. **Living fog (T-245, ADR-0019):** with the device's quality set to Hoch or Mittel (Mittel by default; Aus keeps the still fog above), a shader draws the fog over the map and, for the player view, a margin of one map size around it (`fog-living.ts`): drifting, domain-warped noise in the fog's colours (Bodennebel until T-168) and a faster turbulence at its edge, both scaled to the grid's cells. It reads the soft mask – built with a band of 0.25 to 0.45 grid cells (by edge wobble) instead of the soft edge – and, during a spread, mixes the masks before and after exactly as the fade shader does, so spreads and living fog are one layer. Fail-closed by construction and pixel-tested: wherever the unshifted mask is fog the shader stays opaque, so the wobble and its shifted samples only ever reach into revealed area (the band plus the longest shift – √½ of the warp, diagonally – stay within 0.45 cells, plus up to a mask texel of rounding, so a one-cell corridor keeps its middle open), and the player view keeps the exact hard fog underneath; a hidden pixel looks the same over a black and a white map. The effect renders through a pass-through filter at a share of the screen's resolution (Hoch 0.75 with five octaves of noise, Mittel 0.5 with three) and is stretched. Per frame only its clock (a uniform) changes – the renderer draws every frame while the fog drifts (movement above 0), and a change of the movement alone rebuilds nothing. A change of the look alone (soft edges, quality, edge wobble – same revealed areas) switches at once instead of spreading; with living fog on, the soft-edge switch is disabled, as the living fog always has its own soft edge. The player view's living fog reaches one map size around the map; further out the hard fog is black (seen only when a calibrated TV view goes that far off the map). **Biomes (T-168):** the layer takes the scene's biome – colours, wind (it drifts the noise and draws streaks along the wind), particles (snow, embers, motes, sand; points in grid cells, only over the fog and its band next to the edge, adding to it, never making it transparent) and underglow – with the strength scaling particles, streaks, glow and the heat shimmer (Hitzeflimmern: the edge's turbulence turns into a fast flicker in thin rows, within the same ±0.5 of the warp, so the reach cap holds; never the map); an unknown or missing biome is Bodennebel (own keys only, so a name like "constructor" in a file is no biome). Particle travel is wrapped on the pattern's period, so long sessions stay precise. A change of the look alone (biome, strength, quality, edge wobble – the same polygons on the same map) blends over: the fog shown so far fades out on top of the new layer over the transition time; both cover the same polygons, so nothing hidden shows (harness check). The fail-closed check runs with the biomes that have particles too. Edge wobble and movement are per-device settings like the fade duration; with "reduce motion" in the system and no choice made, the movement starts at 0.2. The DM-window specs of the E2E harness run with still fog (the real clock would make screenshots differ); the renderer harness covers the living fog at frozen moments.
- The renderer draws on demand (once per change), not every frame, so an idle DM window costs no GPU time; animation runs a frame loop only while needed: fades, gliding tokens and living fog that drifts (T-245; movement 0 or quality Aus draws on demand again).
- Video maps (implemented in T-105c): the caller puts the `<video>` directly under the canvas; the renderer sizes it, applies the camera as a CSS `matrix()` and keeps it `visibility: hidden` until a frame was drawn with the fog known – again after a new video, a resize or a lost WebGL context, and for good after teardown. For video maps the canvas is cleared to transparent black (premultiplied alpha). Image maps keep an opaque canvas background.
- Video maps: a positioned HTML `<video>` element underneath a transparent PixiJS canvas, sharing the camera transform; not a texture (ADR-0010, measured in T-007). Image maps are PixiJS textures. Preload the next scene.
- **Vision (stage 5):** visibility polygons per light source and viewer are computed in `core` (pure, 2D raycasting against the resolved walls, closed doors and asset blockers). The TV shows the union of all player tokens' vision; memory fog keeps visited areas dimmed. Blocker types: blocks sight and light, one-way, partial (dimmed instead of hidden).
- **Transitions:** scene changes (crossfade, through black, instant) and soft fog fades stay fail-closed – the incoming scene becomes visible only after its fog is set. Soft fog edges and fades can be switched off in the settings and must meet §11 when on.
- Renderer fixtures in `test-fixtures` are used for screenshot tests.

Maps larger than the GPU's texture limit (T-127): the renderer reads `MAX_TEXTURE_SIZE` (8192 px on many integrated GPUs) and draws a larger image map as tiles that each fit, cut from the image on canvases and placed edge to edge; a map within the limit stays one texture. Video maps are a `<video>` element under the canvas (ADR-0010) and have no such limit. Each tile carries 2 px of its neighbours so scaled sampling shows no seams; tiled and single-texture rendering differ only slightly on thin lines when scaled down (harness check: at most 12 of 255; seams would differ by about 49). A map whose tiles cannot be made shows the "could not be loaded" state in the DM window and leaves the TV black.

## 9. Lighting

- Drivers behind one interface in Rust: `LightDriver { discover, set_state, play_effect }`.
- Zone/role mapping and priority resolution (effect > ambilight > scene) are **pure logic in `core`**; drivers only execute.
- A failing driver reports status; it never blocks the session.
- Photosensitivity limits are enforced centrally before sending to drivers.

## 10. Camera (stage 7)

- Rust pipeline: capture → ArUco detection → homography per camera (calibrated from on-screen markers) → height compensation → grid snap → confidence.
- Fusion of multiple cameras in `core` (pure, testable with recorded detections).
- Output is **suggestions**; `core` decides what is applied (manual locks, confidence threshold).

## 11. Performance budgets

Measured on the reference notebook before each release (not in CI – CI runners have no usable GPU):

| Metric                                                 | Budget                                            |
| ------------------------------------------------------ | ------------------------------------------------- |
| Player view frame rate, 4K video map + fog + 20 tokens | ≥ 60 FPS: ≤ 1 % of frames miss a display refresh¹ |
| Scene switch with preloading                           | ≤ 1 s to first frame                              |
| Command from DM remote/companion → visible on TV (LAN) | ≤ 100 ms                                          |
| Light effect trigger → lamp reacts (HA/WLED/Hue Ent.)  | ≤ 150 ms                                          |
| Desktop cold start                                     | ≤ 3 s                                             |

¹ Measured at 60 Hz output as frame intervals longer than 1.5 × the measured refresh interval (≈ 25.5 ms at 60 Hz). A literal p95 ≤ 16.7 ms is unreachable even at a perfect 60 Hz (interval jitter, timers rounded to 1 ms in WebKit); see `docs/benchmarks/2026-11-17-t007-run2-run3.md`.

The benchmark scene lives in `test-fixtures` (T-105d: a 4K video map, soft fog with holes, 20 tokens, a moving camera; with the frame statistics); `pnpm bench` draws it with the real renderer in the player window while the DM window is open and reports the frame intervals, missed refreshes and dropped video frames (README). The T-007 spike is gone; `pixi.js` is a dependency of `packages/renderer` only.

## 12. Testing strategy

| Layer     | Tool                                                           | Required for                                                                  |
| --------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Unit      | Vitest / `cargo test`                                          | all logic in `core`, `schema`, `storage`, `protocol`; Rust drivers with fakes |
| Component | Vitest + React Testing Library                                 | every non-trivial React component                                             |
| E2E       | Playwright (desktop web build + companion), tauri-driver smoke | every user-facing flow in the task's acceptance criteria                      |
| Visual    | Playwright screenshots of renderer fixtures                    | every renderer change                                                         |

- Coverage gate: **≥ 80 % lines/branches for `core`, `schema`, `storage`, `protocol`**. No fixed gate for UI.
- Screenshot tests run in a pinned Docker image for deterministic rendering.
- Tests must be deterministic: inject time and RNG; no real network in unit tests.

## 13. Security & privacy

- LAN server only; no port forwarding, no cloud relay.
- One-time pairing tokens; DM can kick/revoke any client.
- Companions only receive projected state – never hidden data.
- No telemetry without explicit opt-in.
- The repository is public: test fixtures are self-made or CC0 only (sources in `packages/test-fixtures/SOURCES.md`); no personal or device data in the repo.
- Secrets (e.g. Hue/HA tokens) stored in the OS keychain, never in the sync folder or repo.

## 15. UI shell & design system

_Decided in ADR-0011, ADR-0014 (docked zones), ADR-0015 (themes) and ADR-0016 (sizes in rem, Proposed); binding details in `.claude/skills/ui-design/SKILL.md`._

- **DM window panels (ADR-0017, T-172a; amends the zones of ADR-0014):** a full-width title bar and the ribbon stay fixed at the top; below them the window is made of dockable panels (dockview, free MIT edition – `dockview-react`): Daten (data panel), Karte (the map), Browser, Eigenschaften and Initiative (T-111b: the shown scene's turn order and the tracker's actions). Default layout (DM decision, 2026-11-20): Daten left, the map in the middle, Browser over Eigenschaften over Initiative in a column on the right; a layout stored before the Initiative panel existed keeps working without it, and the View menu shows it. The DM resizes panels by their edges, moves and docks them by their tabs, and shows or hides them from the View menu (macOS menu bar; the title bar's "Menü" elsewhere; Cmd/Ctrl+B for Daten). The layout is stored per device (`dm.layout`, versioned; a layout that cannot be used falls back to the default) and "Layout zurücksetzen" (View menu, settings) restores the default. The map's canvas fills exactly the map panel, so fit, zoom and centring need no insets; the navigation/display dock and the notices float at its bottom. Each panel's menu in its header (T-172b: dock left/right/bottom, float, fold to its title where a neighbour above or below takes the room, hide) does by keyboard what dragging does; the tab's ✕ hides like the View menu. Changes are announced in German through one status line (dockview's messages translated, its open/close messages held back while a command rebuilds a panel). Open scenes are tabs in the title bar (T-223a): each keeps its session and undo history while another shows; only the shown one renders its map, ribbon part and title bar controls. The TV shows the scene the DM sent there ("Szene auf den TV", or the first scene opened while the TV is dark) – switching tabs never changes it, and closing that scene leaves the TV dark. A dot marks a tab whose save is pending or failed (T-223b); only closing one whose save failed asks first. The next start reopens the campaign's tabs (T-114a): after a clean end with the TV's scene on the TV, after a crash or kill with the TV dark until the DM sends a scene. The desktop backend tells them apart (T-238): it creates a marker file in the OS app-data directory at start and removes it on exit; the DM window asks `session_previous_crashed` (the E2E harness, without a backend, uses a marker in device storage). Named layouts (T-172c): the DM saves the current layout under a name per workspace ("Layout speichern …" in the View menu, or settings › Panels, which also renames and deletes them) and switches to one from the View menu; stored per device (`dm.layouts`, versioned, each layout checked like `dm.layout`).
- **Player window:** unchanged – chrome-free fullscreen, no design-system UI. Blackout (T-113a): the dock's "TV schwarz (.)" button or the "." key (not while typing) sends `blackout: true`, and the TV is black over everything while the scene stays loaded, so it comes back at once. TV preview (T-113b): a dockable panel "TV-Vorschau" (in the default layout a tab next to Eigenschaften) embeds the player view itself, fed by `watch` with exactly the messages the TV is sent – so it never shows DM-only data and shows the blackout too – as a scale model of the chosen TV (its shape; the calibration scaled from the TV's physical pixels to the panel). The player view's layers live in `player-view.css`, shared by the TV and the DM window; the initiative bar sizes in container units, so it scales with the preview.
- **Implementation (T-130, T-172a):** `DmShell` owns the zones and exposes them as slots; slots inside panels are stable elements the panels adopt (`SlotHost`), so what renders into them keeps its state while a panel is hidden or moved; components keep their state where it lives (e.g. the open scene in the data panel) and render their parts into a zone with `ShellPortal` (React portal). Outside a shell they render in place, so component tests need no shell. The title bar shows a save status (scenes save on every change), undo/redo and the open scene's tab; the ribbon modes are Szene, Nebel and Anzeige.
- **Fog ribbon and dock (T-131):** the Nebel tab holds the fog tools as ribbon groups – Werkzeug (Verschieben, Aufdecken, Verdecken), Form (Rechteck, Ellipse – drawn from its middle, so it can be put around a token; Shift draws a circle –, Polygon, Lasso, Pinsel with its size; Ellipse and Lasso since T-247, replacing Kreis), keys R, E, P, L, B for the shapes while revealing or hiding (not while typing in a field), Biom (the scene's fog biome and its strength, T-168), Ausbreitung (the spread's speed, T-246) and Ganze Karte (Alles aufdecken/verdecken, and "Nebel ausblenden" – key N – which fades the fog out of the DM window only: a view setting that is never saved, undone or sent; the renderer blends it over like any change of look, T-248) – as toggle buttons with the active one highlighted; the drawing tool's instructions show above the dock while it is active. Rectangles have slightly rounded corners (a quarter grid cell, `roundedRectArea` in `core`), and the brush shows its outline at the pointer at the size it paints (T-170). The ribbon has one height in every tab and workspace (fixed tab row and panel, tools never wrap; a narrow window scrolls the panel sideways), so the map never moves. The dock (bottom centre over the map, a `dock` slot) holds the DM view's zoom out/fit/zoom in/rotate (keys −, 0, +, t; Shift+T turns back – R chooses the rectangle since T-247) and, with a player feed, the TV rotation and the player-view status; notices stack right above it. Popovers and menus open fixed under their anchor (kept inside the window and following it on scrolling), so the ribbon's scrolling panel never clips them; they are clamped again when they grow or shrink (`ResizeObserver`) and when the window is resized (T-166).
- **Workspaces (T-156):** a selector at the ribbon's left end ("ARBEITSBEREICH" over a `Menu`; the open menu is named "Arbeitsbereich" and marks the current workspace as a checked radio item, T-164) switches between the five workspaces of ADR-0017 (T-171): Map Forge (maps), Asset Vault (props, handouts, sounds), Tokens & Kreaturen (player characters and creatures), Campaign Atlas (the current campaign) and the Game-Orchestrator (running a session); each has its own ribbon tabs. The Game-Orchestrator has the modes above; the others show a hint until their own tasks fill them. Its ribbon panels stay mounted while another workspace is shown, so the tools in them keep their state. The workspace last used is kept per device (`dm.workspace`; the ids from before T-171, `assetStudio` and `gameMode`, still open their renamed workspace), the Game-Orchestrator on first start.
- **Controls (T-130b):** ribbon tools sit in `RibbonGroup`s (large icon over a short label, caption below; a caption with ▾ is a `Menu` of less frequent commands). Short follow-up steps (confirm delete, map change) open in a `Popover` under their group instead of growing the ribbon. Plain buttons, fields and selects inside `.dm-ui` get their base look from `components.css` with zero specificity (`:where()`), so component classes always win.
- **Browser and data panel (T-130c):** the scene browser shows one campaign – switched or created from its header menu – as a tree of its scenes, with the open scene's content (map, levels, fog) below it; clicking a scene opens it. New scenes come from the ribbon ("Neu") or the tree's context menu (right-click, Shift+F10, context-menu key) and open in a popover; a new scene opens right away. The data panel is the library's map and asset catalogue (maps with previews since T-124, §6.5); the library folder is chosen in the settings dialog. `DmShell` has no content props: everything, including the data panel and the settings, renders into its slots.
- **Browser (T-158, T-172a):** the Browser panel: its toolbar holds the campaign switch above the tree (compact variant: chevrons, no guides), which starts with the campaign, then Kampagneneinstellungen, Szenen (the open scene with its content), Karten (used by its scenes), Spieler & Charaktere, Handouts & Hinweise and Notizen; empty groups say so. Where it sits and how large it is belongs to the panel layout (T-172a).
- **Details panel (T-159, T-172a):** the Eigenschaften panel (below the Browser in the default layout) shows the facts of what is selected in the browser (campaign and its settings, a scene, a map with the scenes using it, a player). Selecting a scene also opens it; selecting anything else leaves the open scene as it is. Read-only for now.
- **Settings dialog (T-155):** the gear, Cmd/Ctrl+, and the app menu (T-130d) open one modal dialog (`Dialog` in `@dungeon-manager/ui`, layer 50) with categories as vertical tabs on the left and their settings on the right: Darstellung (theme, interface size), Nebel & Animation (soft edges, transition, living fog quality, edge wobble, movement), Bibliothek (library folder) and Panels (Layout zurücksetzen). Focus stays inside it, Escape closes it and focus returns to the gear. Categories come from one list in `DmShell`, so a new one (e.g. Spieleransicht) is one entry; components outside the shell add their settings through the `settings` slot.
- **App menu (T-130d):** the app's commands outside any panel – Neue Kampagne …, Willkommen … and Einstellungen … – come from the native menu bar on macOS (built in the DM window with Tauri's menu API from translated labels; it keeps the system items: edit commands for text fields, window commands, quit) and from a "Menü" button in the title bar elsewhere (Windows, Linux, the E2E harness). Both run the same commands through a small registry (`app-commands.ts`): the part of the window that owns the state registers the handler (the shell the settings, the library panel the new campaign and the welcome dialog). The native menu bar also works while a dialog is open, so every command first closes the open dialogs (welcome, settings) and then opens its own – never two modals at once. The DM window's capability already grants the menu API (`core:default`). Context menus and popovers opened at a point are moved back inside the window before they paint.
- **Welcome dialog (T-153):** every start opens a modal welcome dialog (the same `Dialog`) before the window. Its main area lists the campaigns recently edited on this device, most recent first, each with its last scene and date; a side column holds "Neue Kampagne", "Andere Kampagne öffnen …" and the library folder. Choosing a campaign opens it with its last scene. A campaign that is gone or cannot be read stays in the list, marked, and can be removed from it. On the very first start (no library folder yet) it explains the library and asks for the folder; in a library without campaigns it asks for the first one's name. Escape closes it into the empty window. The list (`dm.recentCampaigns`, at most 8 entries, per library folder) lives in the webview's storage like the theme, not in the library.
- **Sub-scenes in the browser (T-152):** a sub-scene shows under its parent wherever the parent shows (each session, "Ohne Session"); a sub-scene listed in a session without its parent also shows at the top of that session; "Ohne Session" lists only top-level scenes. Right-clicking a scene offers "Neue Unterszene …" (the new-scene popover; the new scene opens under its parent). The rules are pure (`scene-hierarchy.ts`).
- **Sessions in the browser (T-160b):** Sessions lists each session (by date, then name) with its scenes in their order, a scene in several sessions under each, missing scenes as "(fehlt)" and scenes in no session under "Ohne Session"; the open scene shows its content under the place it was opened from. Commands come from the ribbon ("Neu": Neue Szene, Neue Session) and the tree's context menu (new scene in a session, edit/delete a session, move a scene up/down, remove it from or add it to a session), each in a small popover; reordering is keyboard-reachable through the context menu. The tree ids encode the place (`scene:<session>/<scene>`), the tree, details and session changes are pure modules (`campaign-tree.tsx`, `details.ts`, `session-ops.ts`).
- **Notes in the browser (T-161b):** Notizen lists the campaign note and the notes linked from campaign.json, then the session and scene notes (each with its own note and its links). "Notiz öffnen" on the campaign, a session or a scene starts the fixed note if needed and shows it; "Notiz verknüpfen …" links an existing `.md` of the campaign folder; a linked note can be unlinked (the file stays). The details panel shows a note's text as it is (Markdown source, front matter included) and re-reads it when the file changes, e.g. from Obsidian on another device. Links of an open scene wait until it is closed, because the open scene saves its whole state on every change.
- **Notes as Markdown (T-163):** `NoteView` renders a note with `react-markdown` + `remark-gfm` (DM-approved dependencies) and an own remark plugin for Obsidian's `[[links]]`, `![[embeds]]` and callouts; front matter shows as a properties table. Raw HTML in notes is never rendered (`skipHtml`), urls are filtered (`urlTransform`: note links, embeds, relative paths, https only), and links never navigate the window: note links open the note in the details panel, external links only show their address. Images: local ones (relative to the note, or found by name in the campaign folder) come through `library_read_image` – a DM-window-only command that returns image bytes (PNG/JPEG/WebP/GIF by content, ≤ 20 MB) – as blob URLs; `dmlib` still never serves `campaigns/`. External `https` images load only after a click (CSP `img-src … blob: https:`, no referrer).
- **Appearance setting:** follow the OS / light (parchment) / dark (workshop, the default; ADR-0015); stored per device in the webview's storage (OS app-data, not the sync folder) and applied when the window starts, before React renders.
- **Tokens:** CSS custom properties (`--dm-surface-*`, `--dm-border-*`, `--dm-text-*`, `--dm-accent-*`, `--dm-space-*`, `--dm-font-*`, `--dm-z-*`) are defined once in `packages/ui`; apps consume them and never hard-code colours, spacing, fonts or z-indices. The values are data in `packages/ui/src/tokens.ts` (tested for WCAG AA); `packages/ui/styles/tokens.css` is generated from it (`pnpm --filter @dungeon-manager/ui gen:tokens`, a test keeps both in sync). Workshop (dark) is the default; parchment applies when `data-dm-theme="parchment"` is set on the root element, or with `data-dm-theme="system"` while the OS prefers a light scheme (`prefers-color-scheme`); the DM switches it in the appearance setting. `findHardCodedValues` checks app stylesheets.
- **Layering (`--dm-z-*`):** 0 map canvas/video · 10 canvas overlays · 20 floating HUD · 30 ribbon (docked, ADR-0014; the data panel column needs no layer) · 40 context menus/popovers · 50 modals.
- **Themes (ADR-0015):** a dark "workshop" theme (slate surfaces, one gold accent; the default, for a dim room) and a reduced light "parchment" theme; WCAG AA contrast in both. Professional, restrained styling as in a CAD tool: one type family (monospace only for file names and values), small uppercase captions, thin lines instead of boxes and shadows, small radii, one accent for active/selected only, one line-icon set, no illustrative decoration. Fonts and icons are self-made, CC0 or OFL and bundled locally.
- **Density and interface size (T-162):** the DM window is compact by default. All sizes are rem of one base size (`--dm-ui-base-size`, 14px) times the DM's interface size (`--dm-ui-scale`: 90/100/110/125 %, per device, applied before React renders); hairlines and radii stay in px. The spacing grid is therefore 4/8 in quarter rems (3.5/7 px at the compact base, ADR-0016 instead of ADR-0011's literal 4/8 px), and `font-size-xs` never drops below 10px. The map canvas only measures its box, so the interface size never scales the map.
- **Performance:** HUD elements over the canvas avoid costly effects (e.g. `backdrop-filter`) unless the benchmark scene (§11) shows no regression.
- **Previews:** the player-view preview and the next-scene preview are floating HUD panels (layer 20) in the DM window. The player-view preview can additionally open as a separate window on an additional DM monitor; that window gets exactly what the TV gets (`PlayerViewMessage`, same permissions and fail-closed rules as the player window, §8) and shows no controls.
- **Screenshot tests** of the DM window (zone layout) run in the pinned Docker image like the renderer goldens (§12), because the window contains the PixiJS canvas.
- **Companion** reuses tokens and primitives with a single-column touch layout. There is no mobile app (ADR-0013), so no platform-neutral token source is needed.
