# T-007 performance spike – run 1 (2026-11-17)

**Device:** MacBook Air M5 (DM's reference notebook), on power · **Display:** Samsung The Frame 4K TV, connected via HDMI
**Build:** `pnpm spike:desktop` at `82ab15d` (Tauri 2.12 / WKWebView, PixiJS 8.22 WebGL) · **Video:** synthetic 3840×2160, 30 fps, H.264 ~40 Mbit/s

## Analysis

1. **No 4K rendering was measured.** macOS drove the TV at 1920×1080 with devicePixelRatio 1, so "native" and "Full HD" rendered the same 1920×1080 pixels (the spike warned about it). The TV upscaled the 1080p signal itself.
2. **The bottleneck is the video, not fog or tokens.** "Video only" already misses ~47 % of refreshes; adding fog (with blur) and 20 tokens does not make it worse. No repeat degradation, so no thermal throttling within the run.
3. **The pattern points at the 4K video frame upload.** The averages (≈ 45–54 FPS) only add up with many near-zero intervals: long frames (35–48 ms) are followed by immediate catch-up frames. With a 30 fps video, roughly every second display frame receives a new video frame. Uploading a 3840×2160 frame (~33 MB RGBA) into a WebGL texture (PixiJS `VideoSource`, per decoded frame) blocks the main thread, independent of the render resolution. The decoder itself keeps up (0 dropped video frames).

**Interim conclusion:** with the video uploaded as a WebGL texture, the budget is clearly missed – even at 1080p output. Because the cost is isolated to one step with several alternatives, run 2 measures those alternatives before concluding on ADR-0002.

## Next: run 2

The spike gains scenarios for: a 1080p video file (4× smaller upload), WebGPU (GPU-side copy), and the video as a native HTML `<video>` element composited by macOS underneath a transparent PixiJS canvas (no upload at all; the map is the bottom layer anyway, ARCHITECTURE §8). The TV should be driven with a real 4K signal for the native scenarios.
